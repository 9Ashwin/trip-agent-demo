## 一、先破除一个误解

很多人第一反应是：「我把 HTML 改成网页格式，它不就能自己联网了吗？」

**不能。** 这跟文件格式无关，是浏览器的硬性限制：

| 障碍 | 说明 |
|---|---|
| **CORS 跨域** | 浏览器禁止 JS 直接请求携程、12306 等站点 |
| **没有 AI 工具** | 网页里的 JS 没法调用「搜索」这种服务端能力 |
| **API Key 会泄露** | 前端代码用户全都能看到，Key 放前端等于公开 |
| **需要服务端计算** | 搜索 → 解析 → 再喂给模型 → 拼装结果，这串活需要程序在服务器上跑 |

**结论：联网能力必须放在「页面之外」那一层，也就是后端。**

## 二、正确的架构长什么样

```
你的浏览器                     你的后端服务器                    外部服务
┌──────────┐   POST 需求   ┌─────────────────┐   工具调用   ┌──────────────┐
│ 前端页面  │ ───────────→ │  Flask 后端     │ ──────────→ │ 必应搜索页    │
│ (HTML)   │               │                 │              │ (免 Key 抓取) │
│          │ ←─────────── │  ① 保管 API Key │              └──────────────┘
│  显示结果 │   SSE 实时推  │  ② 跑 Agent 循环 │   对话请求   ┌──────────────┐
└──────────┘               │  ③ 真的去联网搜  │ ──────────→ │ 大模型 API    │
                           └─────────────────┘              │ (DeepSeek)   │
                                                            └──────────────┘
```

**分工一句话：前端只负责「显示」，后端才负责「干活」。**

## 三、最核心的机制：工具调用（Function Calling）

整件事的关键，就在 `agent.py` 里这段循环：

```
1. 后端把 web_search 这个工具「告诉」大模型
      ↓
2. 大模型判断：「我需要知道广州到昆明的机票价」
   → 返回一个 tool_call：{ name: "web_search", query: "广州 昆明 机票 9月30日" }
      ↓
3. 后端收到指令，真的去必应搜一页（免 Key），解析出网页摘要
      ↓
4. 把搜索结果塞回对话历史，再问大模型一次
      ↓
5. 重复 2-4，直到大模型说「信息够了」→ 输出最终方案
```

**重点：大模型自己不能上网。** 是它「指挥」后端去搜的。
豆包智能体、扣子 Bot、以及各种「联网 AI」底层都是这个套路。

代码见：
- `agent_langchain.py` → **默认实现**，LangChain v1 `create_agent` 版
- `agent.py` → 后备实现，原生 OpenAI SDK 手写版（同样的循环，但不依赖框架）
- `search_tool.py` → 真正发 HTTP 请求去搜索的那 30 行
- `app.py` → Flask 接口，把每一步用 SSE 实时推给前端

## 三·五、同一件事的两种写法（LangChain vs 原生 SDK）

上面那个循环，项目里给了**两份等价实现**，用 `AGENT_IMPL` 一键切换：

```bash
AGENT_IMPL=langchain   # 默认
AGENT_IMPL=native      # 换成原生 SDK 版
```

两者 `run_agent(payload, emit)` 的签名和返回值完全一致，所以 `app.py` 和前端**一行都不用改**。

**写法的差别：**

| 环节 | 原生 SDK 版（`agent.py`） | LangChain 版（`agent_langchain.py`） |
|---|---|---|
| 循环 | 自己写 `for round_no in range(1, 7)` | `create_agent()` 生成 LangGraph 图，框架自己循环 |
| 工具定义 | 手写 24 行 JSON Schema 字典 | `@tool` 装饰器读函数签名自动生成 |
| 消息管理 | 自己 `messages.append({"role":"tool", ...})` | 框架维护 `state["messages"]` |
| 何时停止 | 自己判断 `if not msg.tool_calls` | 框架判断停止条件 |
| 依赖 | 只要 `openai` | 需要 `langchain` + `langgraph` |
| 可控性 | 每一行都在自己手里，容易调试 | 少写代码，但轮数上限等要自己补 |

**结论：代码量上 LangChain 版更少**（工具定义和消息管理都交给框架了），
但**框架不是白拿的**——下面这三个坑都是实测踩出来的，换 LangChain 前务必知道：

#### 坑 1：`create_agent` 没有 `max_iterations`

老版 `AgentExecutor` 可以直接 `max_iterations=6` 限轮数，v1 的 `create_agent` **没有这个参数**。
不自己数轮数的话，模型会一直搜下去，最后撞上 LangGraph 的 `recursion_limit` 抛
`GraphRecursionError`。本项目在 `astream` 循环里自己计数，到 `MAX_ROUNDS` 就跳出。

> **关于这个上限怎么定**：它是**防止失控的保险丝，不是设计上的限制**。
> 正常一次家庭出行规划，4~8 轮并行搜索就足够覆盖「大交通 / 景点 / 市内交通 / 住宿 / 天气」
> 这五类信息，模型自己会收敛停下来。所以默认给了 **15 轮**，留足余量应对多城市、多程交通。
>
> 想调就在 `.env` 里设 `MAX_SEARCH_ROUNDS`。**不建议调小**——轮数不够时模型会被强行打断，
> 方案质量会明显下降（实测被截断时会退化成「信息不足，请你自行核验」的敷衍输出）。

#### 坑 2：`asyncio.run()` 会让「第 2 个请求」必挂

这是本项目最难查的一个 bug，踩了很久，务必了解。

**症状**：同一个进程里，**第 1 个请求正常，之后每个请求都在 1 秒内失败** ——
每次重新部署后第一个请求又会好，极具迷惑性。用户侧看到的是「一直转圈」，
或者一份「来源 0 个、全靠编」的方案。

**原因**：底层 `httpx` / `openai` SDK 的**异步客户端是按参数全局缓存**的，
它把连接池绑在「第一次用到它的那个事件循环」上。而 `asyncio.run()` 的语义是
「新建一个 loop，跑完就 close」。于是第 2 个请求复用了绑在**已关闭 loop** 上的客户端：

```
RuntimeError: Event loop is closed
During task with name 'model'
```

本地 5 秒复现：

```python
llm = _build_llm("probe")
asyncio.run(ping())   # 第 1 次：成功
asyncio.run(ping())   # 第 2 次：RuntimeError: Event loop is closed  ← 必现
```

**解法**：整个进程共用一个常驻事件循环（跑在后台线程），loop 永不关闭。
见 `agent_langchain.py` 的 `_get_loop()` / `_run_async()`。

> ⚠️ **这里绝对不要改回 `asyncio.run()`。**
> 另外验收时请**在同一进程里连跑两次**请求 —— 只测第一个请求，这个 bug 永远发现不了。

#### 坑 3：兜底分支丢了上下文，模型会说「我没有联网工具」

达到轮数上限或异常后要强制出正文时，如果**只发一条全新的空消息**给模型，
前面搜到的资料就全丢了，模型于是回答：

> 「当前对话环境未提供联网搜索工具，我不能假装已抓取实时票价……」

正确做法见 `_force_final` 与 `_sanitize_for_final`：带**完整历史**收尾，
并把带 `tool_calls` 的消息压成纯对话形式（不传 tools 时，部分网关会因为
「有工具调用记录却没有工具定义」直接报错）。



这是踩出来的真实事故：第一版里，达到轮数上限后我用**一条全新的空消息**去问模型要最终方案，
结果前面 145 条搜索结果**全部被丢掉**，模型于是回答：

> 「当前对话环境未提供联网搜索工具，我不能假装已抓取实时票价……」

用户看到一个「明明搜了 29 次、却说自己不能联网」的方案。

**正确做法**（见 `_force_final` 与 `_sanitize_for_final`）：
把已经搜索到的**完整历史**一起喂回去，并且把带 `tool_calls` 的消息压成纯对话形式
（否则收尾时不给 tools，部分网关会因为「有工具调用记录却没有工具定义」直接报错）。

```python
# 收尾调用：带完整历史，不带工具
resp = await llm.ainvoke(
    _sanitize_for_final(history) + [HumanMessage(content=FINALIZE_HINT)]
)
```

顺带一句：**LangChain 本身不是搜索引擎**，它只是编排框架。它自带的
`TavilySearchResults` / `DuckDuckGoSearchRun` 底层要么要 API Key，要么就是那个国内
连不上的 DDG 接口。所以本项目自己写了 `web_search` 工具（免 Key 必应），再用
`@tool` 挂给 LangChain——**这才是「不用搜索 Key 的 LangChain」的正确姿势**。

#### 方案 D：OpenCode Go 套餐（$10/月，开源编码模型）

[OpenCode Go](https://opencode.ai/docs/go/) 是订阅制的模型网关，走 `/zen/go/v1`。
它有两个**额外要求**（不加会被拒），本项目已用环境变量支持：

```
LLM_API_KEY=你的opencode key
LLM_BASE_URL=https://opencode.ai/zen/go/v1
LLM_MODEL=deepseek-v4.1-flash
LLM_USER_AGENT=trip-agent-demo/1.0      # 必须标识自己的客户端，不能用通用 SDK 名
LLM_SESSION_HEADER=x-opencode-session   # 每段会话要发稳定 session id
```

**两个容易踩的坑：**
1. **模型 ID 必须是带小数点的** —— `deepseek-v4.1-flash`（DeepSeek V4.1 Flash）和
   `deepseek-v4-flash`（DeepSeek V4 Flash）是**两个不同的模型**，写错了会 400/404
2. **缺 `x-opencode-session` 会直接 400**：`MissingSessionID ... cannot be routed efficiently`。
   `agent.py` 里每次请求会生成一个 uuid 作为会话 id

> ⚠️ OpenCode Go 官方说明它「面向 OpenCode 等编码智能体，会监测异常流量」。
> 拿它跑通用网站属于超出设计用途，**自行评估风险**，别做公开服务。
> 当前可用模型列表：`curl https://opencode.ai/zen/go/v1/models`

#### ❌ 已废弃：DuckDuckGo（实测不可用，别再试了）

代码里保留了 DDG 兜底，但实测有**双重问题**：

1. **网络不通** —— `duckduckgo.com` 与 `api.duckduckgo.com` 在国内无法访问，实测连接直接失败（`curl` 得到 `000`）。注意不是沙箱问题：同一环境下 `tavily.com` 返回 302、`baidu.com` 返回 200，说明是被针对性阻断。
2. **接口性质不对** —— 免 Key 只能用 Instant Answer API，它是「百科摘要」接口（返回词条 Abstract 和 RelatedTopics），**不是搜索引擎**。对「广州 昆明 机票 9月30日 价格」这类查询通常返回空。

> **为什么「用 langchain 之类的库」解决不了？**
> LangChain 本身不是搜索引擎，它只是**包装器**。它提供的搜索工具底层要么需要 API Key
> （Tavily / Serper / Bing 官方 API），要么就是同一个 DDG 接口
> （`DuckDuckGoSearchRun`）。真正免 Key 且国内可用的只有：抓取搜索结果页（本项目的必应方案）
> 或自建 SearXNG 实例。

#### 关于百度 / 维基百科

实测均不可用：百度搜索页返回反爬页面（HTTP 200 但只有 1.4KB 空壳），维基百科被网络限制。
所以**免 Key 方案里，必应是目前唯一可用的**。

## 七、部署上线

### 方式一：WorkBuddy 的「发布为应用」（本项目已用这个方式发布）

在 WorkBuddy 里对它说一句「发布这个项目」即可，不用自己买服务器、配域名。
发布前确认两件事：

1. 服务绑定 `0.0.0.0`（本项目 `app.py` 已改好）——绑定 `127.0.0.1` 的话线上访问不到
2. 读取 `PORT` 环境变量（已改好）——部署平台会注入这个变量

### 方式二：自己部署

- **后端**：Railway / Render / 腾讯云 Serverless（都支持 Python + 环境变量）
- **前端**：如果只用静态版，可以单独丢到 Vercel / Netlify
- **环境变量**：Key 配在平台的环境变量面板里，**不要**写进代码或提交到 Git

### ⚠️ 线上版本：搜索无需 Key，但模型仍需 Key

**搜索默认免 Key（必应抓取），所以线上唯一必须配的是模型 Key。**

线上沙箱里没有你的 `.env`。想让**在线版**也能真实联网搜索：

1. 在本地把 `LLM_API_KEY` 填进 `.env`（搜索保持 `SEARCH_PROVIDER=bing` 即可）
2. 重新发布一次（覆盖线上版本）

> 也就是说：**GitHub 上的代码永远不需要带任何 Key**（模型 Key 只放本地/部署环境），
> 而**部署环境可以带 Key**（那才是真正要调用模型的地方）。两边搜索行为完全一致 —— 都是免 Key 必应。

> **安全提醒（重要）**
> 线上版本一旦配了 Key，就等于把「调用额度」公开了 —— 任何拿到分享链接的人
> 都能消耗你的额度。给朋友看 Demo 用**演示模式**就够了。
>
> 本项目内置了按 IP 限流，但**默认是关闭的**（`RATE_LIMIT_PER_HOUR=0`）：
>
> ```
> RATE_LIMIT_PER_HOUR=0      # 0 = 关闭（默认，适合调试和朋友试用）
> RATE_LIMIT_PER_HOUR=20     # 打开：每个 IP 每小时最多 20 次
> ```
>
> 打开后超过配额会返回 `429`，前端提示「请求太频繁了」。
> 只有当你打算把带 Key 的链接**公开给不特定人群**时才建议打开。
> 注意限流是**进程内存**实现，多实例部署需换成 Redis。
>
> 发布前记得确认 `.env` 没有被一起上传（本项目 `.gitignore` 已排除，但仍建议
> 手动核对上传清单）。

### ⏱ 单次规划比较慢，部署时注意请求超时

真实模式下一次完整规划要 **40~90 秒**（要跑 4~8 轮联网搜索，最后还要写几千字方案）。
这带来了一个部署环境才会踩到的坑：

> **反向代理通常有 60 秒的空闲/总时长上限，连接会被直接掐断。**
> 表现是：页面一直停在「运行中」，最后一步永远在转圈，什么错误都不报。

本项目对这个问题做了三重处理：

| 措施 | 位置 | 作用 |
|---|---|---|
| **SSE 心跳** | `app.py`，每 `HEARTBEAT_SECONDS` 秒发一行 `: ping` | 让连接一直有数据流动，避免被按「空闲超时」掐掉 |
| **中断检测** | `static/index.html` | 连接断开但没收到 `done`/`error` 时，前端明确提示「连接中断」而不是傻等 |
| **秒表** | `static/index.html` | 状态徽章显示「运行中 · 23s」，用户知道它没死 |

另外 `done` 事件里带了 `elapsed`，完成时会显示总耗时。

> **调试线上问题的入口：`GET /api/debug`**
> 线上沙箱看不了日志，这个接口会返回 Python / langchain / langgraph 版本、
> Agent 模块能否加载、以及**最近一次异常的完整堆栈**。排查线上问题时先打它。

## 八、常见坑

| 现象 | 原因 | 解决 |
|---|---|---|
| POST 请求返回 **403** | macOS 的 5000 端口被 AirPlay 接收器占用 | 用 5050 端口（本项目已默认） |
| 页面上方一直是「后端未连接」 | 后端没启动 | 先跑 `./run.sh` |
| 一直返回「演示数据」 | 没配 `LLM_API_KEY` | 填 `.env` 后重启 |
| 搜索结果很少 | 用了 DuckDuckGo（国内不通 / 是百科接口） | 配 Tavily 或博查，见第四节 |
| 模型不调用搜索 | 模型不支持 function calling | 换 deepseek-chat / gpt-4o-mini 等 |
| 页面提示「请求太频繁」**429** | 触发了按 IP 限流 | 把 `RATE_LIMIT_PER_HOUR` 设为 `0` 关闭 |
| **页面永远停在「运行中」** | 连接被反向代理按 60 秒超时掐断，且前端没收到结束事件 | 见上式「单次规划比较慢」；本项目已加 SSE 心跳 + 中断检测，重试一次通常能过 |
| 线上报错但看不到日志 | 沙箱日志拿不到 | 打 `GET /api/debug`，里面有最近一次异常堆栈 |

### Q：能不能直接复用 WorkBuddy 的模型能力，不自己的 API Key？

**不能。** 原因：

1. WorkBuddy 是 **客户端 AI 办公产品**，不是模型 API 服务商 —— 官方文档里只列了文档生成、
   数据分析、PPT 生成等能力模块，**没有对外的开放 API / API Key**。
2. 它按**积分套餐**计费（体验版每月 500 积分、标准版 2000 积分……），
   没有提供「按调用量付费给第三方网站用」的接口形态。
3. 架构上它处在**终端**位置：你在 WorkBuddy 里对话，它调用模型、操作你本地文件。
   它不是一个能被别的网站反向调用的中间层。

**那「复用 WorkBuddy 能力」的正确姿势是什么？**

不是在运行时调它，而是在**开发时**用它：

| 你想做的事 | 正确的做法 |
|---|---|
| 生成/修改这个项目的代码 | 直接对 WorkBuddy 说需求，它写代码、跑测试、发布上线 |
| 每天自动跑一次旅行规划 | 用 WorkBuddy 的**定时任务**能力，不用部署网站 |
| 连自己的数据源（邮箱、表格、数据库） | 用 WorkBuddy 的 **MCP 连接器** |
| 做一个给别人用的联网网站 | ← 就是本项目，**必须有自己的模型 Key** |

**一句话：WorkBuddy 是帮你「造工具」的，不是给别人「当零件」的。**

> 顺带提醒：本项目已发布的在线版本用的是**演示模式**（假数据）。
> 想让在线版真实联网，需要在本地 `.env` 填 Key 后重新发布 ——
> 但那等于把调用额度公开了，只给朋友看 Demo 的话没必要。
